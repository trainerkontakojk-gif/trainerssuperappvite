## Requirement

### Problem

On the local image `supabase/postgres:17.6.1.106`, calling a function in an exposed schema whose EXECUTE was revoked from the calling role kills the backend with signal 11. The whole instance then goes through crash recovery, which drops every connection, instead of returning `42501`. This was proven locally through `psql` + `SET LOCAL ROLE authenticated` with 5 of 5 crashes. Upstream #50900 reports the same behaviour through **PostgREST with only the anon key** on 17.6.1.111, including on a production project.

The anon key ships in the frontend bundle. If production runs an affected image, anyone can call `POST /rest/v1/rpc/<fn>` with the anon key in a loop and keep restarting the production database.

**PostgREST path, evidence so far (updated after T1):** (1) **Local 17.6.1.106, full stack, authenticated JWT through PostgREST: crashes.** During TNA T1 the first E2E RPC call with an admin JWT to a function without EXECUTE got `PGRST001`, and the DB log shows signal 11 at 06:34:32 UTC from an `authenticator@postgres` session (`plans/markdown/tna-phase-1-t1-report.md:38`). (2) **Disposable two-container 17.6.1.121 + PostgREST v14.10, anon key: 1 call, clean `401 / 42501`, no crash observed** (`…-t1-report.md` §4). That env was a fresh database without this project's migrations/extensions and without Kong, and its Postgres log window was empty (not even the ERROR line was captured), so it is weak evidence. The two results differ in version, role and environment at once, so they **do not show that .121 is fixed**. #50900 still reports a production crash through the anon REST path on .111. Treat production 17.6.1.121 as possibly affected; the mitigation is required either way, and local E2E security testing is blocked on .106 until it lands.

### Why every affected function is reachable

- PostgREST exposed schemas (local `supabase_rest` container env): `PGRST_DB_SCHEMAS=public,graphql_public`. No migration defines functions in `graphql_public`.
- PostgREST v14.10's routine schema cache (`src/PostgREST/SchemaCache.hs@v14.10`, the function query) filters only on `t.oid <> 'trigger'::regtype AND prokind = 'f'`. It has **no privilege filter**. So every non-trigger function in `public` is routable at `/rpc/<name>` for any role, including anon. The privilege filter applies only to the OpenAPI output.
- Functions returning `trigger` are left out of the cache, so they cannot be called through `/rpc`. Clients have no direct SQL access.
- `pg_graphql` builds its schema per role and leaves out functions the role cannot execute. This is an assumption to be confirmed in T0. It is not the main attack path.

## Design

### D1. Principle

**No function in an exposed schema may have EXECUTE revoked from anon or authenticated.** Access control moves from GRANT/REVOKE into the function: a first-statement guard that raises `42501` before any read, write, or side effect. Functions that no runtime path needs move to a **non-exposed** schema, where PostgREST cannot route to them at all.

Moving a function to a non-exposed schema works **only for functions with no PostgREST caller**. The backend's service-role calls also go through PostgREST, so moving a called function would break the backend. Exposing a private schema with no USAGE would only move the denied-privilege path; whether that path also crashes is unverified, so do not rely on it.

### D2. Shared guard (new non-exposed schema `app_internal`)

```sql
CREATE SCHEMA IF NOT EXISTS app_internal;
REVOKE ALL ON SCHEMA app_internal FROM PUBLIC, anon, authenticated;
-- No USAGE for client roles. Do NOT add app_internal to PGRST_DB_SCHEMAS (local config or production API settings).

CREATE OR REPLACE FUNCTION app_internal.assert_service_role()
RETURNS void LANGUAGE plpgsql STABLE SET search_path = '' AS $$
DECLARE v_role text;
BEGIN
  BEGIN
    v_role := nullif(current_setting('request.jwt.claims', true), '')::jsonb ->> 'role';
  EXCEPTION WHEN others THEN
    v_role := NULL;  -- malformed claims are treated as "not service_role"
  END;
  IF v_role IS DISTINCT FROM 'service_role' THEN
    RAISE EXCEPTION 'SERVICE_ROLE_REQUIRED' USING ERRCODE = '42501';
  END IF;
END $$;
```

- The semantics match TNA D3.2: read only the PostgREST `request.jwt.claims` JSON GUC, never `current_user`/`session_user` (inside SECURITY DEFINER they are not the caller's identity), and accept the exact value `service_role` only.
- It is called only from SECURITY DEFINER functions owned by `postgres`, so it runs with the owner's USAGE and EXECUTE. Client roles never need privileges on `app_internal`. That avoids a second denied-EXECUTE path.
- `ALTER DEFAULT PRIVILEGES` in Supabase grants EXECUTE on new functions to anon/authenticated/service_role in **every** schema `postgres` creates functions in. Explicitly `REVOKE ALL ON FUNCTION app_internal.* FROM PUBLIC, anon, authenticated` anyway. It is harmless, because without schema USAGE they cannot be called, and the schema is not routable.
- Behaviour change: a privileged SQL session (SQL editor, migration) can no longer call guarded functions directly. That is acceptable: no runtime path does this, and there are no cron jobs.

### D4. Migration files

1. `supabase/migrations/<ts>_guard_exposed_service_role_functions.sql`: D2 plus every Group A change, plus Q2/Q3 moves, plus a final verification `DO` block **scoped to the Group A signatures and `app_internal`** that `RAISE`s if any Group A function lacks anon/authenticated EXECUTE or if `app_internal` grants USAGE to a client role.
