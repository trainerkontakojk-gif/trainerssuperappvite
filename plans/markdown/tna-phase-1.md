## Requirement

### Konteks bisnis

TNA mengubah data temuan QA SIDAK menjadi program pelatihan yang terukur: **Data → Temuan → Root Cause → Rekomendasi Training → Target → Evaluasi Pasca-Training**. ### Hasil Fase 1

1. **Daftar parameter** per layanan untuk periode terpilih dengan metrik tingkat, sebaran, tren, penanda kritikal, dan label kandidat. Defaultnya hanya kandidat; toggle **"Tampilkan semua parameter"** (`scope=all`) menampilkan **setiap parameter yang punya baris audit** pada periode terpilih, termasuk yang `findings = 0` (berlabel "Bukan kandidat"; tidak bisa divalidasi karena `POST /tna/needs` menolak `findings = 0`). Bila periode terpilih tidak punya audit sama sekali, daftar diisi parameter dari periode pembanding dengan `auditStatus = "no_audit"` dan metrik `null`, dan respons membawa `selected_audit_status = "no_audit"` sehingga UI menampilkan satu banner "Belum ada audit untuk layanan dan periode ini". (Diputuskan Fajar 2026-10-08 setelah T2.)
2. **Drill-down parameter**: metrik per periode, agent terdampak, klaster root cause (mesin SIDAK yang ada) dan contoh tiket.
3. **Validasi kebutuhan**: penyebab tervalidasi, jenis gap, catatan, keputusan (`training` / `eskalasi_non_training`). Disimpan sebagai `tna_needs` beserta snapshot metrik saat validasi.
4. **Rencana draft** dari kebutuhan `training`: program, judul, jenis intervensi, jadwal, tanggal evaluasi, target, peserta. Bisa diedit selama `draft`.
5. **Aktivasi** rencana: server menghitung ulang dan **membekukan baseline** (populasi + per peserta) serta mengunci peserta.
6. **Detail rencana**: pratinjau baseline (draft) atau baseline beku (aktif), target, peserta, Ringkasan TNA deterministik.
7. Status Fase 1: `draft → aktif`, `draft → dibatalkan`, `aktif → dibatalkan`.

### Di luar cakupan Fase 1

Evaluasi H+30 dan kelompok pembanding, ekspor narasi, penugasan simulasi KETIK/PDKT/Telefun, segmentasi pasca-OJT, narasi AI, UI kelola katalog, akses leader, notifikasi, penghapusan permanen data TNA, entri TNA di `MobileTabBar` (lihat D7).

### Kriteria penerimaan

- Akses dibatasi di nav (rail desktop + drawer mobile), route guard, `requireCapability` backend, dan RLS. Leader/agent mendapat `403` di setiap endpoint `/api/v1/tna/*` dan tidak melihat entri TNA. Admin/trainer **melihat** entri TNA di desktop dan mobile.
- JWT trainer yang memanggil PostgREST langsung **tidak bisa** INSERT/UPDATE/DELETE tabel `tna_*` maupun memanggil fungsi mutasi TNA.
- Angka metrik selalu dihitung server dari **semua** baris (paginasi penuh). Angka dari body request tidak pernah dipakai.
- Phantom tidak pernah dihitung sebagai temuan; agent phantom-only tetap dihitung sebagai agent diaudit.
- Setelah aktivasi, baseline dan peserta **tidak bisa berubah** oleh siapa pun, termasuk `service_role` (ditegakkan trigger).
- Pembuatan rencana + peserta, penggantian peserta, dan transisi status bersifat **atomik**; kegagalan tidak meninggalkan data setengah jadi; dua transisi bersamaan hanya satu yang berhasil.
- Data kurang tampil sebagai "Data belum cukup"; alasan tren kosong dibedakan (D1).
- Status memuat, kosong, gagal (dengan **Coba lagi**), dan sukses tampil eksplisit. Pesan error manusiawi, bukan error database mentah.

## Design

### D1. Definisi metrik (kontrak — jangan diubah tanpa persetujuan Fajar)

Unit analisis: **parameter × layanan × periode**.

- **Pengambilan data:** semua query `qa_temuan` memakai `fetchAllPages` (`apps/api/src/lib/supabase-pagination.ts`) dengan `.order("id", { ascending: true })` seperti `apps/api/src/services/sidak/heatmap-service.ts`. Dilarang query tunggal tanpa paginasi.
- **Kunci parameter:** `qa_temuan.indicator_id` (selalu terisi). Metadata tampilan per periode di-resolve sesuai guardrail: `rule_indicator_id` → `qa_service_rule_indicators` bila ada `rule_version_id`, fallback ke `qa_indicators`. Lihat STOP S1.
- **Agent diaudit** (`auditedAgents`): `peserta_id` distinct yang punya row apa pun (real/phantom) untuk layanan+periode (= `auditPresenceRows`), dikurangi agent non-service via `isAgentExcluded` (`apps/api/src/lib/scoring.ts`).
- **Sesi sampel** (`sampledSessions`) = Σ per agent diaudit dari `max(MAX_SAMPLING, sesi distinct agent)`. Kunci sesi dan `MAX_SAMPLING` (5) **harus diambil dari satu sumber bersama dengan scoring** (`calculateQAScoreFromTemuan`): ekstrak menjadi export bernama di `scoring.ts` hanya jika itu pure lift (S3). **Sesi dihitung dari `scoreRows` per agent** (guardrail SIDAK #3): bila agent punya row real pada layanan+periode itu, hanya row real yang dipakai untuk menghitung sesi; row phantom dipakai hanya bila agent tersebut phantom-only. Agent dengan campuran real + phantom harus menghasilkan `sampledSessions` identik dengan agent yang sama tanpa row phantom.
- **Temuan** (`findings`) = row `findingRows` (real + `isCountableFinding()` dari `apps/api/src/services/sidak/shared-constants.ts`) dengan `indicator_id` tersebut.
- **Tingkat** (`ratePer100`) = `findings / sampledSessions × 100`. Simpan presisi penuh; bulatkan 1 desimal hanya saat tampil.
- **Sebaran** (`spreadPct`) = agent diaudit dengan ≥ 1 temuan parameter ÷ `auditedAgents` × 100.
- **Populasi audit nol vs nol temuan** (dua kondisi berbeda, jangan disamakan):

| Kondisi                                                                                                      | `auditedAgents` | `ratePer100` / `spreadPct`                           | `insufficientData`                 | UI                                                               | Narasi                                                                     |
| ------------------------------------------------------------------------------------------------------------ | --------------- | ---------------------------------------------------- | ---------------------------------- | ---------------------------------------------------------------- | -------------------------------------------------------------------------- |
| **Tidak ada audit** (tidak ada row apa pun, termasuk phantom, untuk layanan+periode; mis. semua row dihapus) | `0`             | **`null`** (tidak pernah `0/0` dan tidak pernah `0`) | `true`, `auditStatus = "no_audit"` | "Belum ada audit untuk layanan dan periode ini", tanpa angka nol | Tidak menyebut angka tingkat/sebaran; memakai kalimat D9 khusus `no_audit` |
| **Audit ada, nol temuan** (mis. clean session/phantom-only)                                                  | `> 0`           | **`0`**                                              | sesuai aturan biasa                | Angka 0 tampil normal                                            | Narasi biasa (`no_findings_both` bila pembanding juga nol)                 |

`auditStatus` dikirim di setiap metrik periode: `"audited"` atau `"no_audit"`. Pembagian dengan nol dilarang di kode; helper metrik mengembalikan `null` sebelum membagi.

- **Periode pembanding:** hingga `compare_count` (default 2, rentang 1–6) `qa_periods` sebelum periode terpilih yang punya `auditedAgents > 0` untuk layanan itu.
- **Tren** — kirim `trendStatus` + `trendPct`:

| `trendStatus`        | Kondisi                                                  | `trendPct`          | Teks UI/narasi                                                            |
| -------------------- | -------------------------------------------------------- | ------------------- | ------------------------------------------------------------------------- |
| `no_current_audit`   | Periode terpilih `auditStatus = "no_audit"`              | `null`              | "belum ada audit pada periode ini"                                        |
| `computed`           | Ada pembanding dan rata-rata `ratePer100` pembanding > 0 | perubahan relatif % | "naik/turun X% dari rata-rata periode pembanding" (stabil bila \|X\| < 5) |
| `new_from_zero`      | Ada pembanding, rata-rata = 0, periode terpilih > 0      | `null`              | "baru muncul; periode pembanding tidak punya temuan"                      |
| `no_findings_both`   | Ada pembanding, rata-rata = 0, periode terpilih = 0      | `null`              | "tidak ada temuan, baik pada periode ini maupun periode pembanding"       |
| `no_comparison_data` | Tidak ada periode pembanding dengan agent diaudit        | `null`              | "belum ada periode pembanding"                                            |

Kelima status saling lepas dan mencakup semua kombinasi. Urutan pemeriksaan: `no_current_audit` → `no_comparison_data` → sisanya. `no_comparison_data`: jika periode terpilih = 0 tanpa pembanding, statusnya tetap `no_comparison_data`. Pembanding > 0 dan periode terpilih = 0 adalah `computed` (−100%). `no_findings_both` tidak pernah menjadi kandidat (gagal `MIN_FINDINGS`), tetapi bisa muncul pada pratinjau draft setelah temuan QA dihapus atau diedit menjadi tidak countable.

- **Kritikal:** kategori parameter `critical` pada periode terpilih.
- **Data belum cukup** (`insufficientData`): `auditStatus = "no_audit"`, `auditedAgents < MIN_AUDITED_AGENTS`, atau `findings < MIN_FINDINGS`.
- **Rata-rata pembanding** hanya memakai periode dengan `auditStatus = "audited"` (sudah dijamin oleh definisi periode pembanding), sehingga tidak pernah merata-ratakan `null`.

Ambang di **satu modul** `apps/api/src/services/tna/thresholds.ts`:

| Konstanta            | Nilai | Makna                                                                           |
| -------------------- | ----- | ------------------------------------------------------------------------------- |
| `MIN_AUDITED_AGENTS` | 5     | Di bawah ini → data belum cukup                                                 |
| `MIN_FINDINGS`       | 3     | Di bawah ini → bukan kandidat                                                   |
| `SIGNAL_SPREAD_PCT`  | 10    | Sinyal _tersebar_                                                               |
| `SIGNAL_TREND_PCT`   | 25    | Sinyal _naik_ (hanya `computed`; `new_from_zero` dianggap naik)                 |
| `CLASS_SPREAD_PCT`   | 30    | Saran intervensi: ≥ 30% kelas, 10–< 30% kelompok kecil, < 10% coaching individu |
| `STABLE_TREND_PCT`   | 5     | Batas "stabil" pada narasi                                                      |

**Kandidat** = `findings ≥ MIN_FINDINGS` dan minimal satu sinyal (`tersebar`, `naik`, `kritikal`). Urutan: kritikal, lalu `spreadPct` menurun, `ratePer100` menurun, nama parameter.

#### D3.2 RLS, grant, dan fungsi mutasi (bergantung K6)

- RLS aktif di keempat tabel. Policy **SELECT saja** untuk `authenticated` dengan `public.is_admin_or_trainer()`. **Tidak ada** policy INSERT/UPDATE/DELETE untuk klien; `REVOKE INSERT, UPDATE, DELETE ON tna_* FROM anon, authenticated`.
- Semua mutasi lewat **lima fungsi publik** di schema `public` (tabel di bawah): `SECURITY DEFINER`, `SET search_path = public, tna_internal`. **Jangan** `REVOKE EXECUTE` dari `anon`/`authenticated`/`PUBLIC` pada fungsi ini (biarkan grant default) — mencabut EXECUTE memicu crash Postgres (K6). Sebagai gantinya, **pernyataan pertama** setiap fungsi publik adalah `PERFORM tna_internal.assert_service_role();`, yang:
  - membaca role dari `nullif(current_setting('request.jwt.claims', true), '')::jsonb ->> 'role'` (klaim yang diisi PostgREST dari JWT bertanda tangan);
  - bila nilainya bukan tepat `service_role` (termasuk `NULL`, kosong, `anon`, `authenticated`, atau klaim tidak bisa di-parse) melempar `RAISE EXCEPTION 'TNA_FORBIDDEN' USING ERRCODE = '42501'` **sebelum** membaca atau menulis data apa pun;
  - tidak pernah memakai `current_user`/`session_user` (di dalam `SECURITY DEFINER` keduanya bukan identitas pemanggil).
- Setelah guard, fungsi menerima `p_actor_id` dan memverifikasi actor ber-role admin/trainer di `profiles` sebagai pertahanan berlapis. Satu fungsi = satu transaksi; error dilempar dengan kode stabil (mis. `TNA_PLAN_NOT_DRAFT`) agar backend memetakan ke `409/422`.
- **Fungsi pembantu dan fungsi trigger** (`assert_service_role`, `require_actor`, `replace_participants`, guard trigger, dsb.) ditempatkan di schema **`tna_internal`**: `REVOKE ALL ON SCHEMA tna_internal FROM PUBLIC, anon, authenticated`, tanpa `GRANT USAGE` ke role klien, dan schema ini **tidak** dimasukkan ke daftar schema yang diekspos PostgREST (lokal maupun produksi). Fungsi publik dan trigger memanggilnya lewat hak pemilik (`SECURITY DEFINER`). Dengan begitu fungsi internal tidak terjangkau lewat API sama sekali, sehingga tidak ada jalur pemanggilan "EXECUTE ditolak" yang bisa memicu crash.
- Tidak boleh ada fungsi lain di schema terekspos yang memanggil `set_config('request.jwt.claims', …)` atau menerima nama GUC dari input pengguna; T1 memverifikasi ini dengan `rg` dan melaporkannya.

| Fungsi                                                                                                             | Isi atomik                                                                                                                                                                                                                                                                                                                          |

- **Trigger imutabilitas** (pola `enforce_simulation_subject_immutable` di `supabase/migrations/20260910000000_simulation_subject_attribution.sql`), berlaku untuk semua role termasuk `service_role`:
  - `tna_needs`: tolak semua UPDATE.
  - `tna_plans`: `baseline_snapshot`, `activated_at`, `need_id`, `program_id`, `created_by` tidak boleh berubah setelah terisi/insert; `baseline_snapshot` hanya boleh berubah dari `NULL` bersamaan dengan transisi `draft → aktif`; field rencana (judul, tanggal, target, intervensi) hanya boleh berubah saat `OLD.status = 'draft'`.
  - `tna_plan_participants`: INSERT/DELETE/UPDATE ditolak bila rencana induk ≠ `draft`, dengan **tepat dua** pengecualian:
    1. **Pengisian pertama baseline peserta**, hanya bila **semua** syarat ini terpenuhi: penanda transaksi `current_setting('tna.activating_plan', true)` sama dengan `NEW.plan_id::text`; `OLD.baseline_findings IS NULL` dan `OLD.was_affected IS NULL`; `NEW.baseline_findings IS NOT NULL` dan `NEW.was_affected IS NOT NULL`; kolom lain (`id`, `plan_id`, `peserta_id`, `peserta_name_snapshot`, `team_snapshot`) tidak berubah. Penanda **tidak** membuka izin untuk mengubah nilai baseline yang sudah terisi, INSERT, DELETE, atau baris rencana lain.
    2. **Pembersihan FK `ON DELETE SET NULL`**: hanya `peserta_id` yang berubah menjadi `NULL`, kolom lain tetap, dan baris `profiler_peserta` lama memang sudah tidak ada (pola `enforce_simulation_subject_immutable`).
  - `tna_activate_plan` memasang penanda dengan `set_config('tna.activating_plan', p_plan_id::text, true)` (lokal transaksi) **tepat sebelum** UPDATE baseline peserta, lalu mengosongkannya dengan `set_config('tna.activating_plan', '', true)` **segera setelahnya** dan sebelum fungsi kembali, termasuk pada jalur error yang ditangkap. Penanda tidak pernah dipasang di fungsi lain.

### D4. Siklus snapshot dan baseline (K7)

| Momen                    | Yang dihitung server                                                                                                              | Disimpan di                                           | Bisa berubah?                                                  |

- Definisi baseline memakai `service_type`, `indicator_id`, `period_id`, dan `compare_count` milik kebutuhan; hanya **waktu hitung** yang berbeda.

Urutan penolakan: bila baseline `auditStatus = "no_audit"`, aktivasi ditolak dengan `422` kode `TNA_BASELINE_NO_AUDIT`: "Belum ada audit pada periode baseline, jadi rencana ini tidak bisa diaktifkan. Batalkan rencana atau pilih kebutuhan lain." ### D9. Ringkasan TNA (narasi deterministik)

Fungsi murni `apps/api/src/services/tna/narrative.ts` (masukan: snapshot, kebutuhan, program, rencana).

> "Tingkat ketidaksesuaian parameter _{parameter}_ ({layanan}) {kalimat tren} dan mencapai {rate} per 100 sesi sampel pada {periode}, terjadi pada {spread}% agent yang diaudit ({n} dari {N}). Penyebab dominan (divalidasi trainer): {klaster} — {cause_note}. Direkomendasikan {program} dalam format {intervensi}, dengan target tingkat ≤ {target} per 100 sesi dan sebaran ≤ {targetSpread}% pada evaluasi {tanggal}."

`{kalimat tren}` mengikuti `trendStatus` di D1 (`computed`: naik/turun/stabil dari rata-rata pembanding {rateBanding}; `new_from_zero`: "baru muncul karena periode pembanding tidak punya temuan"; `no_findings_both`: "tidak memiliki temuan, baik pada periode ini maupun periode pembanding"; `no_comparison_data`: "belum memiliki periode pembanding"). Bila periode narasi `auditStatus = "no_audit"`, **seluruh** kalimat pertama diganti "Belum ada audit untuk parameter _{parameter}_ ({layanan}) pada {periode}, sehingga tingkat dan sebaran belum dapat dihitung." — tanpa angka nol dan tanpa kalimat tren. Bila `insufficientData`: tambahkan "Catatan: data periode ini belum cukup untuk kesimpulan kuat." Draft memakai pratinjau dan diberi awalan "Pratinjau:". Format angka Indonesia (koma desimal).

## 6. STOP conditions (berhenti dan tanya Fajar)

- **S1:** Parameter yang sama punya `indicator_id` berbeda antar periode/versi aturan (cek `qa_service_rule_indicators.legacy_indicator_id` dan data lokal).
- **S2:** JWT admin/trainer tidak bisa membaca `qa_temuan`/`qa_periods`/`profiler_peserta` lewat RLS.
- **S3:** Ekstraksi kunci sesi/`MAX_SAMPLING` dari `scoring.ts` bukan pure lift atau dilarang guardrail SIDAK.
- **S4:** Apa pun yang membutuhkan AI, migrasi/akses Supabase remote, deploy, push, atau data produksi.
- **S5:** E2E tidak bisa dijalankan terhadap target lokal/loopback yang aman.
- **S6:** Kebutuhan menambah/menjalankan test non-E2E — wajib izin Fajar.
- **S7:** Service-role dipakai di luar cakupan K6 (mis. untuk pembacaan TNA atau tabel non-TNA), atau K6 tampak perlu diganti dengan policy INSERT/UPDATE klien. Persetujuan K6 hanya untuk fungsi mutasi `tna_*` di D3.2.
- **S9:** Pengujian guard memicu `signal 11` atau `PGRST001`, atau ada kebutuhan mencabut EXECUTE pada fungsi di schema yang diekspos PostgREST. Jangan mengulang lebih dari sekali; laporkan potongan log.
- **S8:** Ditemukan row `qa_temuan` yang `indicator_id`-nya tidak ada di `qa_indicators`, atau `rule_indicator_id` terisi tetapi `legacy_indicator_id`-nya berbeda dari `indicator_id`. Jangan menebak pemetaan; laporkan jumlah dan contoh ID.
