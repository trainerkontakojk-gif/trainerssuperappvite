# KETIK backend chat status transitions

## Requirement

Continue backend audit finding #2 only: make the session/legacy-turn/durable-response status graph explicit in one SQL transition function, with an expected-state predicate on every status UPDATE. Preserve JWT/owner enforcement, existing row locks, lease tokens/expiry, response context retry/supersede, idempotency, post-expiry goodbye and atomic history finalization. This is policy/maintainability repair, not evidence that the existing locked RPCs have a demonstrated concurrency race.

Lane D: persisted SQL/RPC migration and backend lifecycle architecture. No review-worker, quota/accounting, provider, frontend or new lifecycle statuses. Existing CHECK-constrained status unions remain authoritative; INSERTs initialize rows, transitions UPDATE existing rows.

## Design

- Add one SECURITY INVOKER, service-role-only `transition_ketik_session_status` function with a closed set of named events. It locks the owner-bound session first, then changes only the corresponding session/turn/response status and lease fields. Every UPDATE includes the expected status; lease-dependent events retain token and expiry fencing. Terminal rows cannot be reopened. Failure of a required single-row transition raises PT409 and rolls back the enclosing RPC transaction; best-effort provider failure and bulk expiry/cancellation may legitimately affect zero rows.
- Replace status writes in the latest effective claim/publish/settle/fail/finish RPCs, retaining their business/input validation and response shapes. Remove the unreachable noop INSERT conflict-update path under the already-held session row lock. Keep history creation, transcript publication and transitions in the same transaction.
- Route the legacy HTTP turn failure through a dedicated owner-bound failure RPC rather than a direct table status UPDATE. It delegates to the same transition function; stale failure cannot overwrite a replacement lease or terminal success.
- Add a forward migration and matching rollback which restores the exact prior effective RPC definitions without deleting data. Rollout: apply the migration before deploying the API that calls the new legacy failure RPC. Rollback: stop writes/restore the previous API before reverting the database. No remote apply/deploy is authorized by this task.
- E2E remains real JWT + Hono + Auth/PostgREST/PostgreSQL with only the provider boundary stubbed. A task-owned DB trigger fixture checks the PL/pgSQL call stack for changed statuses during actual HTTP flows; it rejects transition bypasses and is never shipped as a product trigger. Existing E2E cover locks, stale lease publish, retry/supersede, idempotency, authorization and atomic finalization.
